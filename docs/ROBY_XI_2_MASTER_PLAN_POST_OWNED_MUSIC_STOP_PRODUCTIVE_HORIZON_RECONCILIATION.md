### 5. D:\Documentos — current evidence

The current executable architecture already contains two adjacent governed families.

CAP-16 provides local document intelligence and `DocumentInboxManager`.

`DocumentInboxManager.ingest_path()` already supports explicit individual file
admission for bounded text formats and stores normalized governed records.

The official runtime productively builds that inbox through
`build_document_inbox_from_environment()` and its SQLite repository.

Separately, CAP-17 is a certified governed read-only evidence source over one
explicitly authorized injected root. It already owns:

- authorized-root containment;
- read-only collection catalogue semantics;
- bounded local selection;
- document-reading handoff;
- Knowledge and governed Reasoning re-entry;
- CAP-11 evidence continuation.

The registry explicitly warns against creating another catalogue, retrieval,
Knowledge or Reasoning authority.

### 6. Exact D:\Documentos gap

What is missing is not generic document intelligence.

What is missing is not document ingestion.

What is missing is not a second Biblioteca.

The concrete unresolved phenomenon is:

ROBY cannot yet treat `D:\Documentos` as a separately authorized local document
source root while preserving the existing CAP-16 document semantics and the
single-authority collection/retrieval rules already established by CAP-17.

Classification:

`D_DOCUMENTOS_AUTHORIZED_SOURCE_ROOT: UNRECONCILED`

This is now a better-defined residual than the remaining music controls.

### 7. Why direct Document Inbox provisioning is not yet authorized

`DocumentInboxManager` is a record-ingestion authority.

Its environment wiring provisions a database path, not an authorized filesystem
collection root.

Pointing `D:\Documentos` directly at the inbox would leave unresolved:

- root containment;
- traversal policy;
- collection discovery;
- symlink behavior;
- deterministic source identity;
- read-only catalogue semantics;
- whether discovered files are merely indexed or actually ingested.

Therefore:

`DOCUMENT_INBOX_DB_PATH != DOCUMENT_SOURCE_ROOT`

### 8. Why duplicating CAP-17 is forbidden

CAP-17 already solved the governed authorized-root collection problem for Biblioteca.

A new `DocumentsCatalogueManager`, second local retrieval engine or second Knowledge
path would violate the architecture.

The next reconciliation must determine whether:

1. CAP-17 contains reusable instrumental root/catalogue primitives that can support
   a distinct source domain without making Documents a second Biblioteca; or
2. CAP-16 should remain the semantic owner while reusing only the existing governed
   source-root mechanics at an application boundary.

No answer is assumed in this block.
